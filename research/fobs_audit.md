## 4. Функции обработки Telegram-сообщений

Архитектура: бот НЕ на python-telegram-bot, а на прямых HTTP-вызовах Telegram Bot API через `requests` (свой вечный цикл `getUpdates`). Это важно для аудита.

| Функция | Строки | Что делает | Вызывается из | Вход → Выход | Побочные действия | Подтверждение |
|---|---|---|---|---|---|---|
| `get_updates(offset)` | ~464 | Длинный polling Telegram | `main()`, каждая итерация | offset → список апдейтов | нет | нет |
| `handle_message(msg)` | ~818 | Маршрутизатор всех сообщений | `main()`, на каждый апдейт | сообщение → нет | диспатчит дальше | нет |
| `process_with_deepseek(chat_id, user_text, history=None)` | ~739 | Основной ИИ-ответ | `handle_message` (fallback) | текст+чат → ответ/ошибка | пишет в БД историю, логирует настроение при триггер-словах, шлёт ответ | нет |
| `handle_receipt_photo(chat_id, msg)` | ~670 | Обработка фото чека | `handle_message` (если есть photo) | фото → ответ | OCR, запись расхода в БД | нет |
| `ask_deepseek(messages)` | ~476 | Запрос к DeepSeek API | многие | messages → (content, error) | расход API-ключей | нет |
| `ensure_question_at_end(text)` | ~499 | Страховка: добавить вопрос в конец | `process_with_deepseek` | текст → текст | нет | нет |

Команды внутри `handle_message`: `/start /help`, `/morning`, `/evening`, `/checkin`, `/plans /plan`, `/done N`, `/budget N`, `/week /month /today`, `/collect ...` (канал/бот/сайт/instagram/youtube — через mentus_collector). Также распознаёт обычный текст как расход (`число описание`) и план (`план: ...`).

## 5. Система памяти и реальные пути файлов памяти

- `fobs_data.db` — SQLite: таблицы `expenses`, `plans`, `monthly_budget`, `chat_history`, `mood_log`
- `bot_state.json` — offset + даты последних напоминаний
- `fobs_chat_history/chat_history_full.json` + `backup_*.json` — экспорт истории (ежечасно + при старте восстанавливается)

- Память контекста: к DeepSeek идёт `SYSTEM_PROMPT` + последние 8 сообщений из БД + последние 3 записи настроения + до 15 сообщений из архивного JSON

## 6. Подключённые модели и логика переключения

- Единственная модель внутри бота: DeepSeek (`deepseek-chat`) через API `https://api.deepseek.com/v1/chat/completions`, `max_tokens=800` (в mentus_collector — 2000), `temperature=0.75/0.7`
- Переключения между моделями ВНУТРИ кода бота НЕТ. Все обращения идут только в DeepSeek
- Для OCR чеков используется локальный Tesseract (не модель по API)
- Системный промпт (`SYSTEM_PROMPT`) жёстко задан в файле, задаёт личность «Ментус», стиль, правило «каждый ответ заканчивается вопросом»

## 7. Доступ к файлам, серверным командам и процессам

- Полный доступ к своей директории `/root/workspace`, читает/пишет БД, JSON, логи
- Есть доступ к API Telegram (мог бы слать сообщения любому chat_id — внутри код шлёт только своему chat_id)
- `subprocess` импортирован — в главном файле не используется; в `receipt_ocr` вызывает внешний бинарник `tesseract`
- Внешние сетевые запросы: Telegram API, DeepSeek API, t.me/s/..., произвольные URL через `requests` (в коллекторе)

## 9. Планировщик и фоновые задачи

Планировщик — НЕ cron, а самодельный цикл в `main()` с `time.sleep(30)`:
- Ежечасно: экспорт истории в JSON (`export_chat_history_to_json`)
- 08:30 — утренний дайджест (`generate_morning_digest`)
- 11:00, 15:00 — чекины состояния (`generate_checkin`)
- 20:00 — вечернее резюме (`generate_evening_summary`)
- Запоминает дату последних отправок в `bot_state.json`, чтобы не дублировать

## 10. Обработка голосовых сообщений

НЕ реализована. `allowed_updates=["message"]` — бот не принимает голосовые/аудио (только текст и фото). Голосовые сообщения игнорируются. Это слабое место (у тебя есть рабочая транскрипция через Whisper вне этого бота — могла бы быть интегрирована).

## 11. Обработка ошибок

- Много отдельных try/except: каждая функция оборачивает вызовы
- При ошибке DeepSeek: логирует, пишет в БД сообщение об ошибке, шлёт «Связь с мозгами прервалась»
- При ошибке в `main()`: главный цикл обёрнут в try/except → ждёт 10 сек и продолжает
- Ошибка в `get_updates`/`send_message` молча глотаются (except: pass) — сложно диагностировать
- Нет централизованного алерта об ошибках (бот молча пишет в лог, Telegram-уведомления об ошибках нет)

## 12. Логи и формат журналирования

- `fobs_bot.log` — `logging.basicConfig` level=DEBUG, формат `%Y-%m-%d %H:%M:%S - LEVEL - message`, дублируется в stderr (systemd тоже пишет в тот же файл → двойная запись HTTP-строчек, лог раздувается)
- Уровень DEBUG: в лог попадают все HTTP-запросы requests (шумно, лог ~1.9 МБ и растёт)
- Обезличенный фрагмент лога:
```
2026-08-10 16:16:49,630 - DEBUG - https://api.telegram.org:443 "GET /bot[BOT_TOKEN_REMOVED]/getUpdates?timeout=30&allowed_updates=message&offset=969115668 HTTP/1.1" 200 23
```
- Не используется ротация логов: файл растёт бесконечно (weak point)

## 13. Автозапуск через systemd или nohup

- Запущен сервисом systemd: `fobs_assistant_bot.service`
- `Type=simple`, `Restart=always`, `RestartSec=10`, `User=root`, `WorkingDirectory=/root/workspace`, `PYTHONUNBUFFERED=1`
- stdout/stderr → `append:/root/workspace/fobs_bot.log` (двойная запись с FileHandler)
- Процесс жив: `/usr/bin/python3 /root/workspace/fobs_assistant_bot.py` (PID виден в ps)

## 14. Резервное копирование

- Ежечасная выгрузка всей истории в `fobs_chat_history/chat_history_full.json` + ежедневные `backup_YYYY-MM-DD.json`
- Резервные копии: bэкапы `_rev` и рабочие копии договоров/ботов лежат в projects (не относится к этому боту)
- НЕТ автоматического резервирования самой БД `fobs_data.db` (weak point): при сбое диска история расходов/планов потеряется

## 15. Все потенциально опасные операции

Оценка риск/опасность:

| № | Операция | Описание | Риск | Подтверждение |
|---|---|---|---|---|
| 1 | Хардкод секретов | Токен бота и DEEPSEEK_KEY прямо в `.py` | Высокий: при утечке репозитория/лога ключи скомпрометированы. Токен виден в DEBUG-логе (requests логирует URL) | нет |
| 2 | `User=root` в systemd | Бот работает от root | Средний: любой баг/уязвимость в парсинге произвольных URL/чеков может выполнять код от root | — |
| 3 | `subprocess` + tesseract | receipt_ocr вызывает системную команду | Средний: если подсовывают специальный путь — риск инъекции команды (строки не экранируются строго) | нет |
| 4 | Парсинг произвольных URL | коллектор `requests.get(url)` на любой ввод | Средний: SSRF-подобный риск (бот может обращаться к внутренним адресам сети с сервера) | нет |
| 5 | Автоматическая запись расходов | любое «число текст» = расход без подтверждения | Низкий: возможны ложные записи, попадание лишнего в бухгалтерию | нет |
| 6 | Автоотправка сообщений чату | бот сам шлёт в чат по расписанию (08:30/11/15/20) | Низкий: спам, если забыть отключить | нет |
| 7 | Прямой HTTP без асинхронности | блокирующие `requests` в цикле | Низкий: при задержке API бот «зависает» на 30с+ | нет |
| 8 | Нет rate-limit на команды | любой пользователь, вызвавший бота, может тратить API-ключи | Средний: бот не проверяет, что пишет только Артур (кроме ID в командах выгрузки) | нет |

## Сводный список выявленных слабых мест (для докрутки)

1. Секреты захардкожены и попадают в лог (DEBUG показывает URL с токеном) — критично.
2. Нет проверки авторизации: команды и расход DeepSeek-квоты доступны любому, кто напишет боту.
3. Нет обработки голосовых (при том что Whisper-транскрипция у тебя уже есть).
4. Нет ротации логов + DEBUG-шумный requests-вывод → лог раздувается, токен в логе.
5. БД не бэкапится автоматически (только история в JSON).
6. `subprocess`/парсинг URL без строгой валидации, бот под root.
7. Разный код дублируется (два `ask_deepseek`, два набора ключей) — конфиг лучше вынести.
8. Блокирующий requests вместо асинхронного — бот может отставать.
9. Двойная запись логов (FileHandler + systemd append в тот же файл).
10. Расписание в цикле с `sleep(30)`-триггерами по времени — надёжно, но завязано на постоянный аптайм в момент точной минуты.
