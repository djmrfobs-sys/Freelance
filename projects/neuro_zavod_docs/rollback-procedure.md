# Процедура быстрого отката боевого релиза

Использовать, если проблема с продуктом обнаружена ПОСЛЕ переноса со staging на боевой systemd-юнит.

## Шаги (цель — уложиться в 5 минут)

1. **Остановить сломанный продукт немедленно**, чтобы не усугублять:
```
systemctl --user stop <имя-юнита>.service
```

2. **Найти последний рабочий коммит** (если git-версионирование настроено, см. git-versioning-setup.md):
```
cd <путь-к-проекту>
git log --oneline -10
```

3. **Откатиться на последний известный рабочий коммит**:
```
git checkout <hash-коммита> -- .
```
(или `git revert`, если нужно сохранить историю правок, а не просто перезаписать)

4. **Перезапустить на откаченной версии**:
```
systemctl --user start <имя-юнита>.service
systemctl --user status <имя-юнита>.service
```

5. **Проверить health-check** (если реализован по self-test-healthcheck-template.md) — подтвердить, что откаченная версия реально работает

6. **Сообщить пользователю**: что сломалось, на какую версию откатили, что нужно почистить перед повторной попыткой релиза

## Если git не настроен (пока)
Резервный вариант — восстановить конкретный файл/папку из последнего бэкапа в B2:
```
rclone copy b2:reservd/neuro-zavod/<последний-архив>.tar.gz /tmp/
tar -xzf /tmp/<архив>.tar.gz -C /tmp/restore/
# скопировать нужные файлы проекта из /tmp/restore/ поверх сломанной версии
```
Это медленнее (весь архив, не точечный файл) — ещё один аргумент в пользу git-версионирования.

## Правило
Не пытаться чинить "на живую" в боевом юните под давлением времени — сначала откат до рабочего состояния, потом спокойный разбор проблемы на staging.
